# Reproducing the housing numbers

Every figure on the housing page comes out of one file, `housing_data.json`,
built by one script, `underwrite.py`, from public government zips. This document
is how you check it.

```bash
bin/rebuild-housing.sh
```

That downloads the season files (~200 MB on a cold cache, then cached forever —
the registry never revises a closed season), rebuilds the payload, and compares
its SHA-256 against `housing_data.json.sha256`. `--verify` skips the rebuild and
only checks the hash of what is already on disk.

---

## Why this document exists

The page's argument is *check my denominator*. That is not a real invitation
unless the inputs are pinned, because **實價登錄 grows every quarter**. Someone
who runs this pipeline six months from now gets different numbers, and with
nothing to compare against they cannot tell whether they found a bug in the code
or simply newer data. So the build stamps three things into the payload:

| | where | what it pins |
|---|---|---|
| `meta.provenance.version` | printed in the page footer | the code's published contract |
| `meta.provenance.commit` | method section | the tree the build ran from — informational, see below |
| `meta.provenance.source.sha256` | method section + footer | the exact input bytes — the season zips |
| `meta.provenance.refs.sha256` | (from 1.9) | every reference CSV under `data/ref/` — the 內政部, 主計總處 and 中央銀行 series — one entry per file with path, sha256, bytes, and where a `MANIFEST.json` sits beside them, the url and fetch date |

`source.sha256` is a hash over the ordered per-season digests, and the per-file
list is published too, so a single missing or newer season is identifiable
rather than only visible as a mismatch.

**`commit` is not the pin, and cannot be.** A payload cannot contain the hash of
the commit that adds it, so the stamp is always the commit *before* the one
carrying that payload — checking it out gets you the code as it was, not the
artefact. It is marked `+dirty` when the build ran on a modified tree. To
reproduce a specific payload, find the commit whose `housing_data.json.sha256`
matches the one you have:

```bash
git log --oneline -- housing_data.json.sha256 | while read c _; do
  git show "$c:housing_data.json.sha256"; done | grep -n <the hash you have>
```

The authoritative pins are **`version`** (what the code promised) and
**`source.sha256`** (what it read).

## Reading a mismatch

The script prints both hashes and then tells you which case you are in. There
are only three:

1. **Source hash differs.** Your inputs are not the published inputs — usually a
   newer season, sometimes a truncated download. The numbers are *expected* to
   move. Nothing is wrong. (From 1.9 there is a second pin, `refs`: if *that* one
   differs and `source` matches, an official series was re-exported — the MOI
   platform revises history — and only the sections that read it should move.)
2. **Source hash matches, payload hash differs.** The code produced a different
   answer from identical bytes. This is the case worth reporting.
3. **Both match.** Byte-identical. Every number on the page is reproduced.

## What is deliberately not deterministic, and what is

- The bootstrap in `underwrite.py` is seeded (`bootstrap_cis(seed=7)`,
  `build_ladder(seed=11)`), so intervals reproduce exactly.
- The intervals computed in the browser (the MRT distance bins) use a seeded
  `mulberry32`, for the same reason: an interval that moves on every page load
  is not something a reader can check against.
- `geocode` depends on the 內政部 address files under `data/geo/`. They are
  **not** in the source manifest, because they are 100–200 MB and are not needed
  to serve the site — only ~9,800 matched coordinates ship. A build without them
  succeeds and produces a payload with no map. That payload's numbers are
  identical; only `meta.geo` and the `map` block differ.
